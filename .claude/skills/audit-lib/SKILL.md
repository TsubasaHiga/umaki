# ライブラリ全体調査・Issue起票

ライブラリ全体を探索し、潜在的なバグや改修の余地がないか調査してください。

重点ポイント: $ARGUMENTS

## 現在の状況

- Open Issues: !`gh issue list --state open --limit 20 --json number,title,labels`
- 最近のコミット: !`git log --oneline -10`

## 作業ルール

`CLAUDE.md` のガイドラインに従ってください。

要点:
- 起票前に既存Issues（Open + Closed）との重複確認を行う
- 適切なラベル付けを行う
- **Closed済みでnot plannedのIssueと同様の内容は再起票しない**
- プロフェッショナルな目線で、極限レベルで調査・起票する

## アーキテクチャ（3層構成）

```
┌─────────────────────────────────────────┐
│  メインClaude（オーケストレータ）          │
│  - 調査計画の策定                         │
│  - 結果のマージ・重複排除・精査            │
│  - Issue起票の最終判断                    │
└────────┬──────────────────┬──────────────┘
         │                  │
    ┌────▼────┐        ┌────▼────┐
    │ Claude  │        │ Codex   │
    │ 調査隊  │        │ 調査隊  │
    │(複数並行)│        │(codex   │
    └─────────┘        │ exec)   │
                       └─────────┘
```

**メインClaude** は自らコードを調査せず、以下の役割に専念する:
- 調査対象モジュールの割り振り
- 両調査隊の結果を突き合わせたクロスチェック
- 指摘の妥当性判断と既存Issueとの重複排除
- 最終的なIssue起票

## 調査手順

### ステップ1: 調査計画

重点ポイントに応じて調査対象モジュールを決定する。

主要モジュール:
- `src/libs/config/` — グローバル設定（BREAKPOINT等）
- `src/libs/control/` — スクロール制御、動画再生
- `src/libs/convert/` — データ変換（日付、JSON）
- `src/libs/eventControl/` — debounce, throttle
- `src/libs/get/` — 値取得（DOM、UA、計算値）
- `src/libs/is/` — 判定関数（デバイス、要素存在、日付範囲）
- `src/libs/remove/` — 削除ユーティリティ
- `src/libs/security/` — HTMLサニタイズ
- `src/libs/set/` — 設定関数（CSS変数、ストレージ）
- `src/libs/to/` — 型変換
- `src/libs/transform/` — DOM変換
- `src/libs/wait/` — 非同期待機（sleep, メディアロード）

### ステップ2: 並行調査（Claude調査隊 + Codex調査隊）

以下の2つを**並行**で実行する:

#### A) Claude 調査隊（lib-auditor サブエージェント）

`Task` ツール（`subagent_type: lib-auditor`）を使い、モジュールごとに複数のサブエージェントを**並行起動**する。

各サブエージェントには担当モジュールと重点ポイントを指示する:
- コードを実際に読み、ロジックの流れを追跡する
- エッジケース・型安全性・エラーハンドリングに注目する
- テストカバレッジの確認
- エクスポート漏れのチェック

#### B) Codex 調査隊（codex exec — diffベース・速度重視）

`codex exec` CLIコマンドをBashツール経由で実行し、Claudeとは**異なる視点**でコード差分を分析させる。

**重要: Codexには全ファイルを読ませず、差分情報のみを渡すこと。**

##### 手順

1. **オーケストレータ側で差分を事前取得し、一時ファイルに保存**:
   - `git diff <比較基点>..HEAD -- src/` でソースコードの差分を取得
   - 差分を一時ファイルに保存: `/tmp/audit-diff.txt`

2. **プロンプトファイルを作成**:

   以下の内容で `/tmp/audit-codex-prompt.txt` を作成する:

   ```
   プロジェクト: TypeScriptユーティリティライブラリ（ESM/CJS dual output）。
   主要技術: TypeScript strict, Vite, Vitest, Biome。

   以下のgit diffを分析し、変更によって導入された可能性のあるバグ・ロジックエラー・
   エッジケースの未処理・後方互換性の問題を調査してください。
   [重点ポイント: {$ARGUMENTSを挿入}]

   重要な制約:
   - 以下のdiff内容のみを分析すること。ファイルを自分で読みに行かないこと。
   - ツール呼び出しは不要。diffの内容だけで分析を完結させること。

   ライブラリ特有のチェックポイント:
   - エクスポートされた関数のシグネチャ変更（後方互換性）
   - 型定義の品質（any回避、適切なジェネリクス）
   - テストの存在と品質
   - エッジケースの処理

   各問題について以下の形式で報告してください:
   ### [重要度: Critical/High/Medium/Low] 問題タイトル
   - **ファイル**: パス:行番号
   - **カテゴリ**: バグ/型安全性/後方互換性/テスト/パフォーマンス
   - **説明**: 問題の詳細
   - **推奨対応**: 修正の方向性

   <diff>
   {ここにオーケストレータが /tmp/audit-diff.txt の内容を挿入}
   </diff>
   ```

3. **codex exec をバックグラウンドで実行**:

   ```bash
   codex exec "$(cat /tmp/audit-codex-prompt.txt)" \
     --sandbox read-only \
     --skip-git-repo-check \
     -o /tmp/audit-codex-result.txt \
     2>/tmp/audit-codex-stderr.txt
   ```

4. **結果の取得**:
   完了後、`/tmp/audit-codex-result.txt` をReadツールで読み取る。

### ステップ3: 結果のマージ・クロスチェック

1. **収集**: Claude調査隊とCodex調査隊の両方の結果を集める
2. **統合**: 同一の問題を指している発見をまとめる
3. **クロスチェック**: 片方だけが発見した問題は妥当性を確認
4. **重複排除**: 既存の Open Issues と重複するものを除外
5. **重要度ソート**: Critical → High → Medium → Low の順に整理

### ステップ4: 指摘の精査

両調査隊の指摘は**鵜呑みにしない**。各指摘を以下の基準で精査する:
- **妥当**: 実際のコードで確認でき、問題が再現可能 → 起票対象
- **的外れ**: プロジェクト文脈に合わない、過剰、または誤検出 → スキップし理由を明記
- **両方が検出**: 高い信頼度で起票対象とする

### ステップ5: Issue起票

精査済みの問題をGitHub Issueとして起票する。
Issue本文に発見元（Claude/Codex/両方）を記載する。

## 調査観点

指定された重点ポイントに加え、以下を総合的に調査:
- バグ・ロジックエラー
- 型安全性（`any`回避、適切な型定義）
- テストカバレッジ
- エクスポート漏れ
- 後方互換性
- パフォーマンス（不要な処理、最適化の余地）
- ドキュメント（JSDoc、README）
